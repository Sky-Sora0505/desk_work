# セキュリティ設計と脅威モデル

どの層で何を守っているかと、攻撃者の目で見た評価、点検項目です。

最大の弱点は「GitHub アカウントの乗っ取り」です。Tailscale のログインを GitHub に任せているので、GitHub を取られると「自分の端末」として家の中に入られ、ファイアウォールも FileVault も素通りされます。Claude Code へ移って GitHub をより多く使うようになるので、この点はさらに重くなります。

## 10-1. 多層防御

| 層 | 対策 | 破られたときに守るもの |
| --- | --- | --- |
| ネットワーク境界 | ポート開放ゼロ、Tailscale のみ | 無差別スキャンや総当たりを完全に無効化 |
| アクセス制御 | ACL（owner → tag:server の決めたポートのみ）、端末承認、GitHub の2段階認証 | 端末を一台取られても他が守られる。サーバーから手元への横展開もできない |
| サービスのバインド | Docker のポートは Tailscale IP のみ、バックエンドはポートなし | 家の LAN の他の機器（IoT、テレビなど）から見えない |
| 認証 | SSH は鍵のみ・`AllowUsers`・試行3回 | 内側に入られても勝手にログインできない |
| コンテナ | 非 root、読み取り専用、Docker ソケットを渡さない、イメージ固定 | アプリが乗っ取られても周りに広がらない |
| データ | FileVault＋オフライン世代バックアップ（計画） | 物理的な盗難、ランサムウェア |

## 10-2. 脅威モデルの結果（旧「03_レッドチーム脅威モデル評価」より）

設計を攻撃者の目で評価したものです。実機を実際に攻撃した結果ではありません（作った本人が自分の想定で攻めても、本当の安全性は分からないため）。判定は「破れなかった／破りかけた／破った」の3つです。

| リスク | 判定 | 対策と現状 |
| --- | --- | --- |
| インターネットからの直接攻撃 | 破れなかった | 開いているポートがない |
| Tailscale（GitHub）アカウントのフィッシング | **破った**（唯一） | GitHub の2段階認証は確認済み。パスキー化と Tailnet Lock でさらに下げられる |
| 家の LAN 内からの横移動 | 破りかけた | 当初は「書かないものは拒否」に頼る暗黙の守りだった。ACL を明示的に書き、バインドを Tailscale IP に限定 |
| Docker イメージの改ざん（サプライチェーン） | 構造的にゼロにできない | 公式イメージのみ、タグ固定、非 root。依存ライブラリを最小に（KVストアは sqlite-jdbc のみ） |
| SSH への総当たり | 破れなかった | パスワード認証なし。`*:22` は macOS 仕様として受け入れ |
| Tailscale 社の侵害 | 通信内容は漏れない | WireGuard で端末同士が直接暗号化。秘密鍵は端末の中。ただし偽端末を混ぜ込まれるリスクはある → Tailnet Lock |
| 自作 API の無認証 | 受け入れ | Tailscale の内側が自分の端末だけという前提。家族を入れる前に見直す |

2026年には、他社で Tailscale の認証キーが盗まれて攻撃者の端末を大量に登録された事例や、Tailscale SSH の権限昇格の脆弱性（TS-2026-009、1.98.9 で修正）がありました。前者は利用者側の鍵管理の問題です。このサーバーは認証キーを作らず手動ログイン、Tailscale SSH も使っていないので、どちらも直接は当てはまりません。

構築前に行った元の評価には、上の表のほかに次のシナリオがありました。

| シナリオ | 判定 | 内容 |
| --- | --- | --- |
| 家の LAN から SSH(22) と SMB(445) を直接叩く | 破りかけた | macOS の仕様で IP を限定できない2つのポートには到達できる。ただし鍵を持たないと `Permission denied (publickey)` で即拒否され、総当たりする「パスワード」という的がない。認証の強さに頼る守りなので、鍵とパスフレーズの管理が生命線 |
| 日常端末（iPhone など）のマルウェア感染 | 破りかけた | 承認済みの端末は「信頼された内部」なので、サービスには届く。被害はその端末から届く範囲に限られ、サーバーを踏み台に他の端末へは広がらない。日常端末の OS 更新が、サーバー設計とは別に重要 |
| サーバー侵害後の横展開 | 破りかけた（設定漏れを発見） | 当初の ACL は「書いていないから拒否される」という暗黙の守りだった。意図を明示する形に直した（4-2） |

攻撃者から見た総評は「技術的な正面突破は割に合わない。狙うなら人間（フィッシングでアカウントを奪う）か、ソフトウェアの供給元（イメージの汚染）」でした。そのため、次の3つを習慣にします。

- 2段階認証は、パスキーか認証アプリにする（SMS は SIM の乗っ取りで破られ得る）
- Tailscale と GitHub のログインは必ずブックマークから開く。メールの中のリンクは踏まない
- 月に1回、端末一覧に見知らぬ端末や承認待ちがないか見る

実機で確かめるときは、Mac mini から `tailscale ping <iPhone の Tailscale IP>` を打ちます。届かない（ACL で拒否される）のが正しい状態です。

## 10-3. セキュリティの点検項目

次の項目を、導入時と月に1回の点検で確かめます。いまの状態は、公開されるこのフォルダには書きません（自分用のメモは git に入れない `tools/values.local` か、非公開の場所に置きます）。

| # | 点検項目 |
| --- | --- |
| S1 | GitHub の2段階認証が有効か。できればパスキーにする（SMS は避ける） |
| S2 | Tailscale の端末承認がオンか。端末一覧に見知らぬ端末がないか |
| S3 | テスト用に足したファイアウォールの許可が残っていないか |
| S4 | SSH パスフレーズ・FileVault 復旧キー・DB パスワードをパスワードマネージャーに入れているか |
| S5 | `which tailscale` がエイリアスではなくラッパーを指しているか |
| S6 | ACL の `src` が `autogroup:owner` になっているか。使わない予約ポートが残っていないか |
| S7 | Tailscale のアプリ（Mac・iPhone）が最新か |
| S8 | Tailscale と別の VPN アプリを同時に動かしていないか |
| S9 | `status.sh` の公開ポートが Tailscale IP の 3000 と 8081 だけか。`*:` や `0.0.0.0:` が無いか |
| S10 | 倉庫以外の compose（学習用の DB など）も `127.0.0.1` か Tailscale IP にバインドしているか |
| S11 | macOS を今月更新したか |
